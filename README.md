# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать/выключать отопление в своих домах.
- Система поддерживает добавления датчиков температуры, их активировацию / деактивировацию.

**Мониторинг температуры:**

- Система получает данные о температуре с датчиков, установленных в домах. 
- Пользователи могут просматривать текущую температуру в своих домах через веб-интерфейс.

### 2. Анализ архитектуры монолитного приложения

Язык программирования: Go
База данных: PostgreSQL
Архитектурный стиль: монолит (все функции объединены в одном приложении)
Взаимодействие компонентов:
Сервер напрямую обращается к датчикам и реле.
Пользовательский интерфейс (веб-клиент) делает запросы к серверу.
Нет брокера сообщений или асинхронного обмена данными.
Особенности:
Монолит обслуживает все бизнес-функции приложения.
Любое расширение функциональности требует изменения и деплоя всего монолита.
Подключение новых датчиков возможно только через выезд специалиста.

### 3. Определение доменов и границы контекстов

Users Domain
	Что делает:
	Управляет пользователями системы (регистрация, вход, роли, права).
	Позволяет пользователю настраивать свой профиль, подключённые дома и устройства.
	Основные поддомены:
	Auth — авторизация и аутентификация.
	Profile — данные пользователя, настройки, список домов/устройств.
Devices Domain
	Что делает:
	Отвечает за регистрацию, настройку и управление умными устройствами (отопление, свет, ворота, камеры).
	Обеспечивает взаимодействие с устройствами партнёров.
	Хранит текущее состояние устройств (включено/выключено, температура и т.д.).
	Основные поддомены:
	Device Management — добавление/удаление устройства, конфигурация.
	Device Control — управление действиями (включить/выключить и т.д.).
	Integration — взаимодействие с внешними протоколами и API партнёров.
Домен телеметрии (Telemetry Domain)
	Что делает:
	Собирает и хранит показания от датчиков (температура, влажность, состояние).
	Предоставляет API для аналитики, визуализации и сценариев автоматизации.
	Может обрабатывать данные в реальном времени (через очередь или брокер событий).
	Основные поддомены:
	Data Collection — сбор данных от устройств.
	Data Storage — хранение телеметрии.
	Analytics — вычисления и построение графиков (например, температура по времени).


### **4. Проблемы монолитного решения**

Сложность масштабирования: добавление новых функций требует изменения всего приложения и его перезапуска.
Ограниченная расширяемость: невозможно легко подключить новые устройства или модули умного дома.
Отсутствие асинхронности: система неэффективна при большом количестве пользователей и устройств.
Зависимость от специалистов: пользователь не может самостоятельно подключить датчики.
Трудности тестирования и внедрения: изменения в монолите сложно тестировать по частям, высокий риск регрессий.

Если бы монолит был идеально стабилен и количество пользователей/устройств было ограничено, проблем бы было меньше. Но с ростом функциональности и числа клиентов текущая архитектура становится узким местом

# Задание 5. Работа с docker и docker-compose

1) сделать простое приложение temperature-api, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```
